6. TASK C — CONTROLLED SCHEMA EXTRACTION

Compare the following methods.

Method 1: Schema-only dump

Use the approved Supabase CLI version and a properly authorized read-only connection to perform a schema-only extraction.

Expected command pattern:

"supabase db dump --db-url "$DATABASE_URL" -f schema_dump.sql"

Review the installed CLI version and exact supported options before execution.

The connection must not permit database writes.

The output must be inspected for:

- Application schemas and objects.
- Tables and columns.
- Primary and foreign keys.
- Unique and check constraints.
- Indexes.
- Views and materialized views.
- Functions and procedures.
- Triggers.
- RLS policies.
- Grants and ownership statements.
- Extensions.
- Sequences and types.
- Any statements involving data, credentials or platform-managed schemas.

Do not assume that the phrase "schema-only" guarantees the absence of every sensitive or inappropriate statement.

Inspect the output before retaining or using it.

Method 2: Declarative schema generation

Evaluate:

"supabase db schema declarative generate"

Use pg-delta as documented by the installed CLI.

Evaluate whether the approach can represent:

- Tables and columns.
- Constraints and indexes.
- Views and materialized views.
- Functions.
- Triggers.
- RLS policies.
- Comments.
- Domains.
- Roles.
- Publication membership.
- Security-invoker view settings.
- Default grants and privilege overlays.
- Managed-schema customizations.

Use "--strict-coverage" where supported.

If the installed CLI version does not support a documented option, record that fact rather than silently substituting another command.

Review generated files for unsupported objects and incomplete coverage.

Important pg-delta caveat

pg-delta is experimental/pre-1.0 in the relevant workflow. Do not treat successful execution as proof of complete coverage.

Record:

- CLI version.
- pg-delta version, if discoverable.
- Command used.
- Exit code.
- Coverage warnings.
- Unsupported objects.
- Generated file inventory.
- File hashes.
- Any manual adjustments.

Do not modify generated output to hide coverage problems.

8. TASK E — BASELINE SECURITY REVIEW

Review the candidate schema for security-sensitive structures.

At minimum, inspect:

A. Tables and privileges

- Browser-role privileges.
- "anon" and "authenticated" access.
- TRUNCATE, REFERENCES and TRIGGER privileges.
- Table ownership.
- Default privileges.
- Privilege inheritance from the destination environment.

B. RLS

- Tables with RLS enabled.
- Tables with RLS disabled.
- Policies and their commands.
- "USING" and "WITH CHECK" expressions.
- Whether RLS is forced.
- Policy role targeting.
- Potential permissive-policy combinations.

C. Functions and RPC exposure

- Browser-role EXECUTE grants.
- "SECURITY DEFINER" functions.
- Function owners.
- Search paths.
- Dynamic SQL.
- Privileged operations.
- Functions that should not be publicly executable.

Pay particular attention to previously identified functions, including:

- "is_admin(uuid)"
- "get_admin_metrics_summary(timestamptz)"
- "run_achievement_checks(uuid)"

Do not invoke sensitive production RPCs to test their behavior.

D. Views

- Security-invoker versus security-definer behavior.
- Underlying table access.
- Browser-role exposure.
- Whether views unintentionally bypass intended RLS boundaries.

E. Storage and managed schemas

- Bucket definitions.
- Storage object policies.
- Custom triggers or functions attached to managed schemas.
- Any relevant "auth.users" triggers.

Do not copy actual storage objects or production files.

F. Extensions

- Confirm required extensions and versions.
- Identify extension dependencies.
- Record platform-managed extensions separately.

Distinguish confirmed risks from unverified possibilities.

Do not describe a grant as an exploitable vulnerability without evidence of an actual reachable attack path.
