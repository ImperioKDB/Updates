# Scope

The migration adds an operational analytics record for confirmation-email requests made by Scholars. Its stated purpose is to distinguish Auth requests that were accepted, requests that failed, and accepted requests associated with accounts that later became confirmed. The migration explicitly preserves the distinction between Supabase Auth accepting a request and an email provider delivering a message to an inbox.

The migration covers:

- A new `public.auth_confirmation_email_events` table.
- Three supporting indexes.
- Row-level security enablement on the table.
- Replacement of one admin-only `SELECT` policy.
- A JSON-returning analytics function covering summary, daily, and recent-event data.
- Function privilege revocation from `public` and an execute grant to `authenticated`.
- A descriptive table comment.

It does not contain seed inserts, updates, deletes, dynamic SQL, calls to external URLs, provider API calls, triggers, views, materialized views, grants on the table itself, or changes to existing columns/constraints outside the objects declared here.

## Function

`create or replace function public.get_auth_confirmation_email_analytics(p_since timestamptz, p_until timestamptz)` creates or replaces a `public` function with:

- return type `jsonb`;
- language `plpgsql`;
- `security definer` execution mode;
- `set search_path = public, auth`;
- function body that validates the range, checks admin status, reads event rows, joins `auth.users`, and returns three JSON sections.

The function raises `Invalid confirmation analytics range` if either bound is null or `p_since >= p_until`. It raises SQLSTATE `42501` with message `Admin access required` if `public.is_admin(auth.uid())` is false.

The returned JSON object contains:

- `summary`: integer counts for `accepted`, `failed`, and accepted events whose joined Auth row has a non-null `email_confirmed_at`; `pending` is `greatest(accepted - confirmed, 0)`; `confirmation_rate` is zero when there are no accepted events, otherwise the confirmed/accepted percentage rounded to one decimal place.
- `daily`: an array grouped by `date_trunc('day', requested_at)::date`, ordered by day, with accepted, failed, and confirmed counts. It is `[]` when there are no rows.
- `recent`: up to 100 rows in descending `requested_at` order, exposing event id, timestamp, request kind, request status, email domain, error code, whether the associated Auth user is confirmed, and the Auth confirmation timestamp. The email hash is not returned.

The function uses left joins to `auth.users`, so events with a null `user_id` or no matching Auth row remain eligible for analytics and are treated as not confirmed. The confirmation association is evaluated at query time from `auth.users.email_confirmed_at`; the migration does not snapshot a confirmation event or create a separate confirmation record.

The function's `security definer` setting is a security-sensitive mutation. Its explicit search path is `public, auth`, which reduces search-path ambiguity compared with an unset path, but the file does not set an owner, revoke function privileges from other roles beyond `public`, or qualify every built-in function reference. The admin check is performed inside the function even though the table has an admin policy.

# Security/ordering implications

The primary security boundary is the combination of RLS and the admin predicate. RLS is enabled, and the declared read policy permits selection only when `public.is_admin(auth.uid())` returns true. The function is `security definer`, but it repeats the admin test before reading data, which is important because the function is executable by the broader `authenticated` role. The function's output contains operational and account-confirmation information, so the admin check is material.

The function's fixed `search_path = public, auth` is a positive hardening measure, but it is not equivalent to a complete security review. The file does not set a trusted owner, explicitly revoke all table privileges, revoke execute from every possible role, or qualify every built-in/operator reference. A reconstruction should preserve the function's definer/invoker semantics, search path, explicit signature, and privilege statements rather than approximating them with an ordinary invoker function.

The policy is dropped and recreated by name. This makes the migration idempotent for that named policy, but it can overwrite a prior definition with different semantics. `create or replace function` likewise replaces the named signature's body and security attributes. The `if not exists` table/index clauses avoid duplicate-object errors but can conceal drift from the expected schema. The policy and function statements are therefore not purely additive in a pre-existing database.

The `on delete set null` foreign key preserves event rows after an Auth user deletion, but makes confirmation attribution dependent on the continued presence of the referenced Auth row. Since confirmation is derived live from `auth.users.email_confirmed_at`, an account's later state can change the analytics result without any event-row mutation. Null or unmatched users count as unconfirmed in the function's `confirmed` calculations.

The function enforces a half-open time interval (`>= p_since` and `< p_until`) and rejects invalid ranges. Daily grouping uses the database/session interpretation of `timestamptz` for `date_trunc`, so timezone/session settings can affect day boundaries if not standardized by callers or the deployment. The recent query orders twice and applies a 100-row limit in the inner query; the outer aggregation preserves descending order by `requested_at`. Ties on timestamp have no explicit secondary ordering, so tie ordering is not guaranteed.

The function reports `pending` as accepted minus confirmed, floored at zero. This is an analytics convention, not proof that each accepted request is still pending delivery or that each confirmed account corresponds uniquely to an event. Multiple accepted events for one user can inflate counts; the migration declares no uniqueness constraint or deduplication rule.
